# Publish the intranet route to IIS, and roll it back (Module 2)

**Status: lab environment only.** This machine (Windows 11, `WORKGROUP`) has no IIS role installed
(IIS Express only), so none of these commands was run here. They are the procedure for the lab
server (IIS 10 with the *Windows Authentication* role service, the ASP.NET Core 10 Hosting Bundle,
a domain `CONTOSO`, DNS `accessops.contoso.test` pointing at the server, a TLS certificate for that
name). What was run here is the same application on Kestrel with the Negotiate handler
(README, "Verified here").

All commands run in an **elevated** PowerShell on the IIS server. `appcmd` is
`$env:windir\System32\inetsrv\appcmd.exe`.

```powershell
$appcmd = "$env:windir\System32\inetsrv\appcmd.exe"
```

## 0 · Prerequisites check

```powershell
Get-WindowsFeature Web-Server, Web-Windows-Auth            # both Installed
dotnet --list-runtimes | Select-String AspNetCore.App 10.  # Hosting Bundle present
```

`Web-Windows-Auth` missing = no `windowsAuthentication` module; enabling the section then fails or
IIS answers 401.2 to everyone. Install it (`Install-WindowsFeature Web-Windows-Auth`) — a server
change, done by the server owner.

## 1 · Rollback baseline first (before changing anything)

```powershell
& $appcmd add backup "accessops-m2-before"                 # one-step restore point of applicationHost.config
New-Item -ItemType Directory -Force C:\lab\accessops-m2 | Out-Null
& $appcmd list site /config /xml          > C:\lab\accessops-m2\baseline-sites.xml
& $appcmd list apppool /config /xml       > C:\lab\accessops-m2\baseline-apppools.xml
& $appcmd list config -section:system.webServer/security/authentication/anonymousAuthentication /xml > C:\lab\accessops-m2\baseline-anonymous.xml
& $appcmd list config -section:system.webServer/security/authentication/windowsAuthentication   /xml > C:\lab\accessops-m2\baseline-windows.xml
```

If the public sign-in site already exists (Module 4/5: e.g. site `AccessOps Public`), record its
state too — it must stay Anonymous:

```powershell
& $appcmd list config "AccessOps Public" -section:system.webServer/security/authentication/anonymousAuthentication
& $appcmd list config "AccessOps Public" -section:system.webServer/security/authentication/windowsAuthentication
```

## 2 · Publish to an isolated site with its own pool

```powershell
dotnet publish "Module 2\AccessOps\AccessOps.csproj" -c Release -o C:\inetpub\accessops\intranet

& $appcmd add apppool /name:"AccessOps Intranet" /managedRuntimeVersion:"" /processModel.identityType:ApplicationPoolIdentity
& $appcmd add site /name:"Lab Intranet" /physicalPath:"C:\inetpub\accessops\intranet" /bindings:"https/*:443:accessops.contoso.test"
& $appcmd set app "Lab Intranet/" /applicationPool:"AccessOps Intranet"

# TLS: bind the certificate for accessops.contoso.test (thumbprint from the lab CA)
netsh http add sslcert hostnameport=accessops.contoso.test:443 certhash=<thumbprint> appid='{4dc3e181-e14b-4a21-b022-59fc669b0914}' certstorename=MY
```

The published `web.config` (generated by the Web SDK) registers `AspNetCoreModuleV2` with
`hostingModel="inprocess"`. The data folder is `AccessOps:DataRoot` (`../AccessOpsData` by default):
give the pool identity `IIS APPPOOL\AccessOps Intranet` Modify on that folder only, outside the
site root.

Record (deliverable "effective settings"): binding `https *:443 accessops.contoso.test`,
pool `AccessOps Intranet` (No Managed Code, ApplicationPoolIdentity), target framework `net10.0`
(`AccessOps.runtimeconfig.json` → `Microsoft.AspNetCore.App` 10.0.x), authentication state before
the change (from step 1; a new site inherits the server defaults: Anonymous on, Windows off).

## 3 · Apply the scoped Windows-only settings

Either paste `iis/windows-auth.location.xml` into `applicationHost.config`, or set the same values
with `appcmd ... /commit:apphost` (which writes the same `<location path="Lab Intranet">`):

```powershell
& $appcmd set config "Lab Intranet" -section:system.webServer/security/authentication/anonymousAuthentication /enabled:false /commit:apphost
& $appcmd set config "Lab Intranet" -section:system.webServer/security/authentication/windowsAuthentication /enabled:true /useKernelMode:true /commit:apphost
& $appcmd set config "Lab Intranet" -section:system.webServer/security/authentication/windowsAuthentication /-"providers.[value='Negotiate']" /commit:apphost 2>$null
& $appcmd set config "Lab Intranet" -section:system.webServer/security/authentication/windowsAuthentication /-"providers.[value='NTLM']" /commit:apphost 2>$null
& $appcmd set config "Lab Intranet" -section:system.webServer/security/authentication/windowsAuthentication /+"providers.[value='Negotiate']" /commit:apphost
& $appcmd set config "Lab Intranet" -section:system.webServer/security/authentication/windowsAuthentication /+"providers.[value='NTLM']" /commit:apphost
```

Effective settings to attach (deliverable 1):

```powershell
& $appcmd list config "Lab Intranet" -section:system.webServer/security/authentication/anonymousAuthentication
& $appcmd list config "Lab Intranet" -section:system.webServer/security/authentication/windowsAuthentication
```

Expected — intranet: `anonymousAuthentication enabled="false"`, `windowsAuthentication
enabled="true" useKernelMode="true"`, providers `Negotiate`, `NTLM` in that order; public route:
Anonymous `enabled="true"`, Windows `enabled="false"` (unchanged). See `effective-iis-settings.md`.

**Do not** put these sections in the site's `web.config`: on a default install they are locked at
server level and IIS answers **500.19** ("This configuration section cannot be used at this path").
If you see 500.19, read the file and section it names, remove them from `web.config`, and set the
values here at `apphost` level (or in IIS Manager, which writes the same location). Do not unlock
the sections to make the error go away.

The application code needs no change for IIS: `AddNegotiate()` on an in-process IIS host forwards
to IIS Windows Authentication when it is enabled on the server, and asks for it to be enabled when it
is not (Microsoft docs; not run here). `Program.Main` reads the same `Application.User`.

## 4 · Health check after the change

```powershell
Invoke-WebRequest https://accessops.contoso.test/ -UseDefaultCredentials -UseBasicParsing | Select StatusCode   # 200
```

## 5 · Rollback (restore the saved settings)

One step:

```powershell
& $appcmd restore backup "accessops-m2-before"
```

Or, value by value, back to the baseline files of step 1 (for a site created in step 2, that is
the server default):

```powershell
& $appcmd clear config "Lab Intranet" -section:system.webServer/security/authentication/anonymousAuthentication /commit:apphost
& $appcmd clear config "Lab Intranet" -section:system.webServer/security/authentication/windowsAuthentication /commit:apphost
```

Then confirm the site answers again (step 4 without `-UseDefaultCredentials` now returns 200 with
Anonymous back on) and diff `appcmd list config ... /xml` against the baseline files. To remove the
lab site entirely: `appcmd delete site "Lab Intranet"`, `appcmd delete apppool "AccessOps Intranet"`.

## Local equivalent (what runs on this machine)

| IIS (lab) | Kestrel on this machine |
|---|---|
| Anonymous off, Windows on | `AddAuthentication(NegotiateDefaults.AuthenticationScheme).AddNegotiate()` + `FallbackPolicy = DefaultPolicy` (every request challenged) — `AccessOps/Startup.cs` |
| Providers Negotiate, NTLM | the Negotiate handler offers only `WWW-Authenticate: Negotiate` (observed); SPNEGO falls back to NTLM inside it for a local account |
| Windows Authentication not enabled (misconfiguration) | `--AccessOps:WindowsAuthentication=Off` → anonymous request reaches `Program.Main` → `HostFaultPage` |
| rollback | stop the process; nothing on the machine was changed |
